Tiered Precision and Speculative Prefetch for Local MoE Inference

What actually happens when you try to run a 30B mixture-of-experts model on one consumer GPU that's too small for it — including the idea that worked and the one that didn't.

System SuperVRAM (llama.cpp-based) Hardware RTX 3090 24GB, WD SN550 NVMe Date September 2026 Evidence class measured_rtx3090

Abstract

SuperVRAM is a VRAM+RAM+SSD expert cache for running mixture-of-experts (MoE) language models larger than available GPU memory on a single consumer GPU, built as a fork of llama.cpp. This report covers two pieces of work built and measured on real hardware: first, a popularity-tiered mixed-precision quantization scheme that downgrades the least-predictable transformer layers to 4-bit while keeping the rest at 8-bit, selected from real routing traces rather than an arbitrary split — measured at 3.1× higher decode throughput than the 8-bit baseline, and 1.26× higher than an equally-sized arbitrary-split control, at a quality cost of +0.73% perplexity. Second, a C++ port of a confidence-gated speculative expert-prefetch scheduler, previously validated only in Python simulation — built, correctness-verified bit-exact under real load, and then measured to regress throughput by 12.5% in the system's actual SSD-bandwidth-bound regime, with the cause diagnosed rather than assumed. Both results are reported with the same rigor: every claim in this document is backed by a repeatable command and a JSON artifact, not a benchmark run once and rounded up.

1. Background & system

The problem: a mixture-of-experts model like Qwen3-30B-A3B has 48 layers of 128 experts each, but only 8 experts fire per token per layer. Its full weights don't fit in a 24GB consumer GPU — but at any given moment, most of those weights are dead code. SuperVRAM exploits that: a bounded set of expert slots lives in VRAM, backed by direct-I/O reads from SSD on a cache miss, with LRU/LFU eviction.

Every configuration in this cache — resident, RAM-cached, SSD-cached — is verified to produce bit-identical token IDs and logit hashes against full-GPU execution before any throughput number is trusted. This is the same discipline both pieces of work below inherit: a benchmark number is not believed until correctness is checked first, separately.

In the regime this system targets — one request, one GPU, a model that doesn't fit — the dominant cost is not compute. Across every cold-cache benchmark in this project's evidence ledger, 72–81% of decode time is spent waiting on the SSD. That single fact is the thread connecting both results below: one exploits it, the other was defeated by not accounting for it.

2. Popularity-tiered precision

The idea: not all layers are equal, so don't quantize them equally. Use real routing data to decide which layers can afford to lose precision, instead of picking an arbitrary split.

2.1 Design

Each of the 48 layers is assigned to one of two tiers — Q8_0 (“hot”) or Q4_K (“cold”) — using a popularity signal computed from 3,276 tokens of real routing traces. The literal formula the original spec called for (average number of experts activated per token) turned out to be degenerate on this model: Qwen3's router always fires exactly 8 experts, so that signal is ~8.0 for every layer with no discriminating power at all. The signal that was actually used instead is the entropy of each layer's expert-usage distribution — how concentrated vs. diffuse a layer's routing is across its 128 experts — which does vary meaningfully (6.14–6.62 bits across layers on the real trace set). 24 layers with the lowest entropy (most concentrated, “specialist” routing) are kept at Q8_0; the other 24 are downgraded to Q4_K.

2.2 Correctness gates

Four gates, run in order, before any throughput number was trusted:

✓Byte accounting— 25.2 GB total (down from 32.5 GB Q8_0 source), 0 precision mismatches across 144 tensors
✓Gate exactness— all 48 router tensors bit-exact vs. the Q8_0 source
✓Quality— 96.97% top-1 token agreement, +0.73% perplexity vs. Q8_0 (full Q4 costs +2%)
✓Throughput— measured on real hardware, cold-SSD protocol, 3 reps

2.4 The honest complication

The mechanism is not what the spec hypothesized. Top-1 agreement and perplexity are statistically indistinguishable between the popularity split and the arbitrary control — if anything the arbitrary split is marginally better on quality. The popularity signal earns its win on throughput, not quality: it happens to pick a mix of layers the runtime's LRU cache serves more efficiently for this workload, not a mix that better preserves accuracy. That's a real, reproducible effect — just not the effect the original spec predicted, and the write-up was corrected to say so rather than let the original hypothesis stand uncontradicted.

3. Speculative prefetch, ported to C++

The idea: predict which experts will be needed next and start loading them from disk before they're asked for, so I/O wait hides behind other work. Confidence-gated, so a bad guess costs a wasted read instead of corrupting the cache.

3.1 What was built

A confidence-gated scheduler (AdaptiveSpeculativeScheduler) existed only as a validated Python simulation before this work — 44 unit tests, a 3,600-run simulated ablation matrix, never run against real hardware. It was ported into the real classic/SSD tier of llama.cpp's expert cache, behind a new --moe-expert-scheduler {off,ass} flag (default off, verified bit-exact no-op). The port includes a background worker thread that reads speculative candidates into a staging buffer without ever touching cache bookkeeping directly — that mutation happens only on the main thread, at a defined commit point, avoiding any data race with the required (non-speculative) cache path.

3.2 Two bugs the port caught by checking against the real reference

Stale prediction reuse

The Python reference consumes (removes) a pending prediction once resolved; a first C++ draft only read it, which would silently reuse a stale prediction on a second call. Caught by generating reference values from the actual Python code, not by hand.

Float vs. double precision

Two confidence values that are conceptually both “2/3” can land on different doubles depending on which arithmetic path reached them — and the gate's tie-break logic depends on that residual difference. A first draft used 32-bit floats; fixed to 64-bit doubles, verified bit-exact against the Python reference's own floating-point representation.

Empty-slots-only admission was permanently inert

The safest-looking policy — never evict, only fill empty cache slots — turned out to never fire past the first few steps, because a warmed-up cache simply has no empty slots left. Confirmed via instrumentation: issued=0 across 256 tokens. Fixed by allowing eviction of an LRU-eligible victim, with two-part re-verification at commit time to avoid evicting something genuinely needed in the interim.

3.3 Correctness, under real load

256-token decode, prefetch genuinely active (not the trivial off-vs-off case): 23,574 speculative reads issued, 23,571 committed — and tokens plus logit hashes identical to --moe-expert-scheduler off across all 256 steps. The additive-only design (it only ever warms extra cache slots; it never changes which expert gets computed for a required step) held up under real, heavy exercise, not just the case where nothing fired.

12.5% slower, 27% more SSD traffic, and no improvement in the required path's own hit rate — if anything slightly worse, from occasionally evicting an expert that was needed again shortly after. The mechanism itself worked exactly as designed (98.6% of issued reads landed successfully); the extra bandwidth was overwhelmingly wasted, not misapplied.

3.5 Root cause, diagnosed from the data

The ported gate's budget is denominated in compute time, faithfully matching the Python design — which implicitly assumes an overlap regime where I/O hides behind spare GPU compute. But this system's actual regime is SSD-bandwidth-bound (Section 1): there is no compute slack to hide anything behind, so every speculative byte directly competes with required bytes on the same physical drive. A compute-time budget structurally cannot see that contention, so the gate kept firing — and in this regime, firing was close to a coin flip that cost real bandwidth either way. The fix this points to — denominating the budget in spare SSD bandwidth instead of compute time — is a different design, not a parameter tweak, and was not attempted here.

4. Related work

Neither idea is unprecedented. Both sit in active, recent (2025–2026) research areas, with at least one close, independently-published match for each.

SPICE (arXiv 2608.21240)
Submitted Aug 2026 · accepted ASP-DAC 2027

A near-identical idea to the prefetch scheduler — confidence-gated adaptive lookahead with a low-rank fallback — published essentially the same week this project's Python simulator was built. Measured on real multi-GPU hardware, DeepSeek-V2-Lite and Qwen2-57B-A14B, up to 3.12× speedup in TPOT. Independent convergence on the same principle; SPICE has the hardware validation this project's C++ port also now has — just not the same result.

ggml-org/llama.cpp issue #20757
Open, unimplemented feature request

Describes almost exactly the core three-tier VRAM/RAM/SSD cache this project ships, down to recommending SLRU as the eviction default — something this project's own policy ablations found makes <1 point of difference vs. plain LRU. The llama.cpp community has been asking, unanswered, for the system underlying this report.

GEMQ, MODE, EAC-MoE, QuantMoE-Bench
2024–2026 academic work on importance-aware expert quantization

Multiple papers in this family flag that routing frequency doesn't reliably predict quantization sensitivity — exactly what Section 2.4 found empirically: the popularity signal helped throughput, not quality, contradicting the naive hypothesis that motivated it.

FareedKhan-dev/kimi-k3-in-c
From-scratch C99 inference engine, 2.78T-parameter Kimi K3

A larger-scale, independently-built peer project solving the same shape of problem (stream a model too big for RAM from disk). Reports “80% of a token is waiting for a disk” — nearly identical to this project's own 72–81% figure — and deliberately chose a simple static admission policy over predictive prefetching, a quiet piece of corroborating evidence for Section 3's own finding.

5. Honest assessment

What this is, and isn't

Neither result is conceptually novel at the idea level — both land in active research areas with recent, sometimes independently-converging prior art. What's real here is measured, verified evidence on actual consumer hardware: a working 3.1× speedup you can use today, and a negative result reported with its actual cause diagnosed instead of hidden. The honest framing is “built, measured, and correctly attributed two real results on a single consumer GPU” — not “solved a problem nobody else has solved.”

The negative result is not a lesser finding than the positive one. A confidence-gated prefetch design copied faithfully from a validated simulation, that turns out to regress performance for a specific, diagnosed reason (a compute-time budget in a bandwidth-bound regime) is exactly the kind of result that prevents someone — including a future version of this project — from re-discovering the same dead end the slow way.
