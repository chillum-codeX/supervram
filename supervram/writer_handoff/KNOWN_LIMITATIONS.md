# Known limitations and failure modes

1. The compact GPU cache copies host mmap pages to device slots. It is not SSD-to-VRAM DMA. cuFile on this machine is compatibility-mode host bounce.
2. Prompt ubatches can select up to `min(n_expert, n_tokens * top_k)` distinct experts. v1 fails loudly when that exceeds `n_slots` (llama-bench `-ub 16` returned decode `-3`). Decode with `-ub 1` stays within top-k.
3. Q4_K_M fits in 24 GiB, so cache cannot beat full GPU residency there; it is the correctness/overhead reference. Q8_0 (30 GiB) is the case where cache competes with `--cpu-moe` / mmap.
4. Cold-cache short runs copy several GiB and look slower than mmap; warmed llama-bench decode is the fairer comparison.
5. Linux page cache is not a hard RAM budget. mmap/cache minimize eager reads but do not cap system RAM.
6. BAR1 is 256 MiB; Resizable BAR is not in effect. Idle PCIe is gen2 x16.
7. CUDA graphs were disabled for bring-up (`GGML_CUDA_DISABLE_GRAPHS=1`).
8. No prefetch, no double-buffered staging ring (one pinned staging buffer, synchronized before reuse), no llama-server cache metrics.
9. Cross-framework throughput comparisons still require matching quantization, context, batch and output length.
10. Early `svram-verify` decode timings (before the `llama_synchronize` fix) were inflated; only the 256-token sweep in `results/rtx3090/ablations-long/` and `llama-bench` numbers are valid.
11. The ablation covers decode at `-ub 1` from a warm page cache with 3 repetitions and one prompt; long contexts and prompt processing are not covered.
12. Direct I/O is Linux-only (`--moe-expert-direct-io`, `--moe-expert-io-threads`, `--moe-expert-staging-mib`; the `SVRAM_*` environment variables are a fallback). `llama-bench` does not have the flags yet. The 13.9 t/s cold result is one model, one prompt, decode only, and about 0.14x of an estimated (unmeasured) native 48 GB card.
13. The dense non-expert weights (about 1.3 GiB for Q8_0) still pass through the page cache once at load time; expert data does not.
14. The adaptive speculative prefetch scheduler (`supervram/scheduler.py`, `PLAN_ADAPTIVE.md`) is a pure-Python simulation prototype validated only in the deterministic trace-replay harness. It has not been ported to the C++/`ggml_backend_sched` integration, so item 8's "no prefetch" for the real cache is still accurate today.
15. The scheduler's gate formula defines "expected cost of a wrong read" as a budget-pooled top-k selection (rank all candidates in the lookahead window by calibrated confidence, spend a shared per-window compute-time budget on the most-confident ones first) rather than a literal per-candidate cost term, because an earlier per-candidate inequality (`p_use * t_read < budget - (1 - p_use) * t_read`) was found to algebraically cancel `p_use` out of the comparison entirely -- caught by an end-to-end run showing higher waste than the baseline it was supposed to beat, not by inspection.
16. The roofline cost model (`scripts/cost_model.py`) has no drive-contention term: a wasted (fired-but-never-used) prefetch is modeled as costing nothing beyond the bytes it occupies, though a real drive queue would make it compete with other reads. This is optimistic for ASS and, if anything, understates its own overhead relative to what real contention would show.
17. The gate's firing behavior is not monotonic across the full `--drive-gbps` range: ASS's modeled-throughput advantage over blind prefetch widens over a middle range of simulated drive speeds and then narrows back toward parity at very slow ones, because the gate correctly refuses to fire anything once no candidate's read fits the fixed per-window compute budget (a safe floor, not a broken result, but not literal unbounded "the gap widens as the drive slows down" either).
18. `--prefetch-depth` in ASS mode is spent as one shared budget across the whole lookahead window (the top-k most-confident candidates total, not top-k per layer in the window) so that "equal depth" comparisons against `--scheduler off` stay fair; a wider `--lookahead-d` therefore broadens the ranking pool rather than proportionally increasing how many candidates can fire.
19. ASS's modeled throughput is *not* universally >= blind prefetch's -- an earlier claim to that effect (and a test docstring saying so) was based on one hand-picked weak-predictor scenario. The full 3,600-run scaled ablation matrix (`results/ablation-simulate-ass-scaled/`, see `docs/IMPLEMENTATION_STATUS.md`) found 65/2,304 comparable rows (2.8 %) with worse modeled throughput than the baseline, up to -33.5 %. 63 of those 65 use `predictor=oracle`: the scheduler's confidence calibration starts neutral and needs a few observations to warm up to a predictor's real accuracy, so against an already-perfect oracle that warm-up window causes the gate to wrongly refuse some correct prefetches. Against every other (realistic, weak) predictor in the matrix, only 2/1,920 comparisons regressed (0.10 %, noise). The gate's cost is a real, if small, warm-up tax paid against strong predictors, not a free lunch against every predictor quality.
20. Of the matrix's `waste_bytes` "ASS worse than baseline" cases (432/2,304, 18.8 %), 397 (92 %) are rows where the baseline fired nothing at all (`off_waste = 0`) and ASS fired something small -- the comparison metric can read as a regression even when the absolute bytes involved are minor and no throughput cost follows (0 of the 208 `predictor=markov` "worse" cases also showed a throughput regression).
